# 網站手動驗收

先以 `npm run build` 產生最新 production build，再執行 `npm run preview`，使用輸出的 loopback URL。預覽 server 沒有 SPA fallback；`/resume` 不公開，相關本機預覽檢查使用 `npm run dev`。

Browser tests 會以本機回應替換遠端圖片，因此測試結果不代表第三方服務可用。

依改動影響選擇驗證範圍，並在執行紀錄分別標示已測與未測的範圍：

- 瀏覽器與裝置包含適用的 Safari、Firefox 與真實手機，不能從 Chromium 結果推定其他環境已通過。
- 導覽與版面包含相關 hash 直接開啟、reload、返回與前進路徑、breakpoint 及放大設定。
- 鍵盤與輔助工具包含焦點順序、開關後的焦點行為，以及適用的 screen reader。
- 列印包含 OS 列印對話框、PDF 畫面、文字完整性與閱讀順序，以及聯絡與社群連結。
- Service worker 變更包含歷史 registration、controller 與既有安裝環境的升級行為。

經歷與成果數字的來源查核依 [Resume Skill](../../.agents/skills/resume-writer/SKILL.md) 處理，不能把 repo 內重複出現的敘述當成獨立事實證據。外連的目的地與服務可用性需分別檢查，不能由測試使用本機替代圖片推定外站可用。

每次記錄瀏覽器、viewport、語言、紙張設定與 commit，結果寫入 commit 說明與交付回報。未執行或已知失敗的項目不能回報為通過，既有問題依 [Roadmap](../../docs/roadmap.md) 記錄，另行依 SDD 的 `change` 或 `plan` 流程修復。

## SITE-R2.3 返回與前進

原因：需要人工確認視覺、裝置操作或外部目的地，自動測試不能取代完整判斷。

步驟：

1. 點選首頁的 About。
2. 記錄 URL 與頁面落點。
3. 捲動到 About 區塊中途。
4. 記錄 URL 與閱讀位置。
5. 點選 Header 的 Projects。
6. 記錄 URL 與頁面落點。
7. 按瀏覽器返回。
8. 確認回到 About 原本的閱讀位置。
9. 按瀏覽器前進。
10. 確認回到 Projects。

預期結果：明確點選區塊連結後使用返回與前進，URL 與閱讀位置依對應歷史紀錄恢復，包含區塊中途的位置，不因 scroll 更新而連續新增紀錄。

## SITE-R2.8 窄版選單

原因：需要檢查實際觸控、鍵盤接續及短螢幕中的選單操作。

5. 按 Escape。
6. 再次開啟選單。

8. 按 Tab。
9. 重新開啟選單。
10. 點擊 Header 外部。
11. 將畫面放大至桌面寬度。
12. 將畫面縮回手機寬度。

預期結果：選單內容可捲動，控制不重疊；Escape 關閉並還原焦點至按鈕，選取連結後焦點與 Tab 順序從目標內容接續，外部點擊與桌面寬度會收起選單。一般 Tab 可離開選單。

## SITE-R2.9 Header 組成

步驟：

1. 在 320、390、720、721、1024、1440、1920、2560px 寬度檢查 Header。
2. 切換另一個語言。
3. 重做各寬度的檢查。

預期結果：Logo 與內容入口有清楚層次，Header 與 Projects 對齊，寬螢幕上的內容保持置中；窄版文字完整、控制不重疊、操作範圍至少 44px 高，焦點提示清楚可見。Header 的材質隨白灰背景自然變化，文字或圖片經過下方時仍清楚，底線保持柔和；選單展開時，Header 與選單使用實色背景；瀏覽器支援並收到減少透明度或提高對比偏好時，Header 也使用實色背景。

預期結果：閱讀區的長段落、Projects 與 Blog 完整清晰且不漂移；取得與失去焦點時，作品與文章維持當下捲動位置的位移、尺度及不透明度；聚焦期間捲動仍連續更新，焦點提示可辨識。

## SITE-R13.10 捲動與效能

2. 以 PageDown、PageUp 及方向鍵捲動。
3. 快速捲動後反轉方向。
4. 在實機 iOS Safari 以觸控重做往返操作。
5. 在效能工具錄製一次完整捲動。
6. 檢查停止捲動後的更新。

預期結果：保留原生捲動速度與方向，沒有額外等待、強制定格、新增水平溢出或可見卡頓；停止後不持續執行動畫更新。真實手機驗收見 [Roadmap](../../docs/roadmap.md#真實手機履歷下載驗收)。

## SITE-R18.1 依情境共用焦點框

原因：需要人工判斷中性導覽、內容互動與深底焦點的調性，以及不同尺寸控制的框線留白。

步驟：

1. 以英文介面及 1440 × 900 視窗開啟 production build。
2. 用 Tab 與 Shift+Tab 依序瀏覽 Header、Hero、About、Projects、Blog 與 Footer。
3. 用方向鍵選取作品。
4. 檢查該作品分頁、展示區及外連的焦點。
5. 對另外兩個作品重做相同檢查。
6. 用鍵盤開啟 QR code dialog。
7. 按 Escape 關閉 dialog。
8. 切換繁中介面。
9. 將視窗改為 390 × 844。
10. 展開窄版選單。
11. 重做相同的鍵盤操作。
12. 執行 `npm run dev`。
13. 開啟本機 `/resume`。
14. 以鍵盤檢查列印按鈕與紙張內的連結。

預期結果：焦點框共用 2 px 實線並保留控制原有圓角，配色與留白依以下規則顯示：

- Header、主要內容 landmark 與履歷預覽使用深灰。
- 首頁內容及 QR code dialog 使用深橄欖綠。
- Footer 使用淺橄欖綠。
- 一般控制的外距為 3 px。
- 文章卡片與作品展示區的外距為 5 px。
- 滿版導覽目的地使用 2 px 內框。

## SITE-R18.2 深淺背景辨識

原因：需要人工判斷實際背景、控制輪廓與容器裁切，computed style 不能取代可見範圍檢查。

步驟：

1. 以 1440 × 900 視窗開啟首頁。
2. 用鍵盤聚焦白灰底上的一般連結、履歷下載與作品主要按鈕。
3. 聚焦 Blog 文章卡片與深灰 Footer 的社群入口。
4. 重新載入首頁。
5. 按 Tab 聚焦跳過導覽連結。
6. 按 Enter。
7. 檢查主要內容容器在視窗內的側邊焦點框。
8. 以鍵盤啟用 Header 的區塊連結。
9. 檢查目的地的側邊焦點框。
10. 對 Header 的其他區塊連結重做相同檢查。
11. 將視窗改為 390 × 844。
12. 重做上述檢查。

預期結果：不透明閱讀狀態下的焦點框清楚，與相鄰背景對比至少為 3：1。填色按鈕沿用所屬區域的焦點色，外距隔開填色與框線；滿版目的地的邊線留在 viewport 內，沒有新增裁切或水平溢出。

## SITE-R18.3 系統強制色彩

原因：Chromium 的 forced-colors 模擬不能取代 Windows 系統高對比模式的實際顯示。

步驟：

2. 開啟 production build。
3. 用鍵盤操作 Header 與窄版選單。
4. 用鍵盤操作作品分頁、展示區、文章及 Footer。
5. 用鍵盤開啟 QR code dialog。
6. 按 Escape 關閉 dialog。

預期結果：各區域均使用系統焦點色，實線框持續可見；品牌色不覆蓋訪客的系統設定，內外距仍讓焦點位置可辨識。
