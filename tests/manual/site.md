# 網站手動驗收

先執行 `npm run build` 與 `npm run preview`，從電腦開啟 preview 印出的本機網址。從實機驗收時，使用該裝置能連到的同一 commit 的版本，並記錄網址。檢查本機履歷預覽時，以 `npm run dev` 開啟 `/resume`。

依改動選擇情境，搭配[自動驗證](../../docs/verification.md)執行。記錄 commit、瀏覽器與版本、裝置、視窗尺寸、語言、相關偏好或列印設定，以及實際結果。區分已測、未測與失敗的範圍。實機、螢幕閱讀器與 OS 列印分別回報，待處理事項放在 [Roadmap](../../docs/roadmap.md)。

## SITE-R2.3 返回與前進

原因：確認實際瀏覽器的歷史紀錄、閱讀位置及修飾鍵行為。

步驟：

1. 在兩種語言的桌面與窄版畫面記錄起始 URL 與閱讀位置。按「關於」或 About，確認落在 Header 下方。
2. 捲到 About 中途並記錄位置。桌面另用快跳切換段落，比對前後的 URL 與 `history.length`。
3. 按 Header 的 Projects，再用瀏覽器返回與前進，分別比對 About 的閱讀位置及 Projects 落點。
4. 以 Cmd 或 Ctrl 點選 Header 的 Blog，核對新分頁的落點與來源頁的位置。

預期結果：瀏覽器恢復各筆歷史紀錄的網址及閱讀位置，包含 About 中途的位置。快跳保持 `#about` 及相同的歷史筆數。

## SITE-R2.4 Hash 直接開啟

原因：確認字型及內容載入後，瀏覽器仍維持 hash 落點或閱讀位置。

步驟：

1. 分別在新分頁開啟 `/#home`、`/#about`、`/#projects`、`/#blog`，檢查 hash、目前區塊提示及 Header 下方的落點。
2. 在各區塊重新載入，再捲到區塊中途重載一次。比對兩次重載前後的落點。
3. 還原後自行捲動，再調整視窗大小，檢查頁面是否被拉回原先的還原位置。

預期結果：在新分頁開啟各首頁 hash 時，目標內容不被 Header 遮住；重載後保留原本的閱讀位置，兩種操作的目前區塊提示都與內容一致。

## SITE-R2.6 常駐 Header

原因：需要判斷初始畫面、捲動、觸控及鍵盤操作中的可發現性。

步驟：

1. 在首頁首次載入時檢查 Logo 與導覽。逐段往下捲動並操作 Header 的內容連結。
2. 縮至手機寬度，捲過首頁後再開啟選單，操作各區塊連結。

預期結果：Header 的位置固定，初始畫面與捲動後都可操作；內容落點不被遮住。

## SITE-R2.8 窄版選單

原因：需要檢查實際觸控、鍵盤接續及短螢幕中的選單操作。

步驟：

1. 在 320 px 寬的短視窗展開 Header 選單。嘗試捲動選單，操作內容連結與語言切換。
2. 重新展開選單，用 Tab 進入內容連結，按 Escape。選單有提示時，檢查兩次 Escape 的各自結果。
3. 重新展開，按 Enter 選取內容連結，再按 Tab 檢查接續位置。
4. 分別重開選單，測試點擊外部、用 Tab 移出 Header，以及放大到桌面再縮回手機寬度。

預期結果：選單內容可捲動，控制不重疊；Escape 關閉並還原焦點至按鈕，有提示時依 SITE-R19.2 先關閉提示。選取連結後焦點與 Tab 順序從目標內容接續，外部點擊與桌面寬度會收起選單。一般 Tab 可離開選單。

## SITE-R2.9 Header 組成

原因：需要判斷實際文字、留白、對齊及放大後的視覺品質。

步驟：

1. 在 320、390、720、721、1024、1440、1920、2560 px 寬度檢查雙語 Header，並用桌面瀏覽器的頁面縮放功能，在 200% 下重做。比對 Logo、置中容器、Projects 對齊、控制尺寸與焦點。
2. 以滑鼠、觸控及鍵盤操作控制。讓文字和圖片分別從白色與灰色區塊捲入 Header 下方，檢查清晰度。
3. 展開窄版選單，核對 Header 與選單都採實色背景，然後關閉選單。
4. 在支援的瀏覽器啟用減少透明度，核對 Header 的實色背景後還原偏好。
5. 在支援的瀏覽器啟用提高對比，核對 Header 的實色背景與分隔線。

預期結果：Logo 與內容入口有清楚層次，Header 與 Projects 對齊，寬螢幕上的內容保持置中；窄版文字完整、控制不重疊、操作範圍至少 44 px 高，焦點提示清楚可見。Header 的材質隨白灰背景自然變化，文字或圖片經過下方時仍清楚，底線保持柔和；選單展開時，Header 與選單使用實色背景；瀏覽器支援並收到減少透明度或提高對比偏好時，Header 也使用實色背景。提高對比偏好會加深 Header 與選單的分隔線。

## SITE-R4.5 鍵盤切換語言

原因：確認鍵盤可到達切換器、看見焦點，並使用兩種按鍵切換。

步驟：

1. 用 Tab 與 Shift+Tab 聚焦語言切換器，檢查焦點提示。
2. 用 Enter 切換，再用 Space 切回。核對每次操作後的文字與語言標示。

預期結果：使用 Tab 找到原生語言按鈕，以 Enter 或 Space 切換；不需要滑鼠。

## SITE-R5.1 個人摘要

原因：兩份字典可使用同一份錯誤資料，故需對照作者提供的資料。

步驟：

1. 在兩種語言逐一比對 Hero 的姓名、目前職稱與公司、學歷及學位。資料位置見[內容來源](../../docs/architecture.md#where-to-edit-content)。
2. 依[履歷編輯規範](../../.agents/skills/resume-writer/SKILL.md)比對作者提供的事實，有矛盾時向作者確認。

預期結果：在兩種語言載入首頁，姓名、目前職務的職稱與公司、教育資訊均與負責資料一致。

## SITE-R5.3 Email 複製

原因：確認滑鼠與手機原生選取後能貼上完整地址。

步驟：

1. 用滑鼠選取 Hero email 並貼到純文字編輯器，比對完整地址。
2. 在實機手機長按地址、複製並貼到其他 app，核對結果。

預期結果：Hero email 可原生選取並複製完整地址。

## SITE-R5.4 社群與學校

原因：確認外部頁面的實際目的地及分頁行為。

步驟：

1. 逐一開啟 Hero 的 GitHub、LinkedIn、Cake 與學校連結，比對新分頁的 URL 與頁面內容。
2. 返回來源分頁，確認原頁仍可操作。

預期結果：操作 Hero 的 GitHub、LinkedIn、Cake 與學校連結，新分頁目的地符合負責來源。

## SITE-R5.6 Hero 閱讀與行動層級

原因：需要人工確認視覺層級、頁內連結提示與跨語言閱讀順序。

步驟：

1. 在桌機及手機的兩種語言中，依序查看姓名、職務、問候、主要行動、學歷與聯絡資訊。
2. 用滑鼠及鍵盤操作 Projects 連結，核對外觀與頁內落點。將游標移到職務及學歷，比對回饋並開啟學歷連結。

預期結果：主要行動先於補充資訊；Projects 具有細底線並前往頁內區塊，靜態職務與學歷連結的操作提示可以區分。

## SITE-R6.3 Footer 內容

原因：確認雙語署名、顯示當年度的版權、聯絡內容及外部目的地。

步驟：

1. 在兩種語言核對 Footer 的聯絡說明、完整 email、平台連結、署名與版權年份。
2. 開啟平台連結以核對目的地，再從 Footer 複製聯絡文字並貼上核對。

預期結果：Footer 顯示目前語言的聯絡說明、完整 email、GitHub、LinkedIn、Cake、作者識別與版權，不顯示服務清單；年度及姓名正確，目的地維持。

## SITE-R6.4 外部部落格

原因：確認外站載入的是完整筆記列表。

步驟：

1. 在兩種語言開啟 Blog 的完整筆記入口，核對新分頁的內容與 URL。
2. 返回原頁，檢查閱讀位置。

預期結果：Blog 的完整筆記入口以新分頁開啟 `https://blog.byc1999.com/list`。

## SITE-R6.5 本機品牌圖片

原因：需要目視確認 Hero 公司標誌、尺寸與載入失敗時的版面。

步驟：

1. 在 320、390、1440 px 寬度及兩種語言核對公司標誌、比例與預留尺寸。
2. 在開發者工具封鎖標誌的請求，停用 cache 並重新載入，查看標誌原本的位置及相鄰文字。

預期結果：公司標誌與目前任職公司一致，比例正確。載入失敗時保留原空間，沒有失敗圖示，職稱與公司文字仍可閱讀。

## SITE-R6.6 Footer 郵件入口

原因：原生 mailto 的處理取決於作業系統與使用者的郵件 app 設定，自動測試只能確認連結與鍵盤入口。

步驟：

1. 在兩種語言用 Tab 聚焦 Footer email，核對名稱、地址與焦點。拖選並複製地址，再貼上核對。
2. 在已設定郵件 app 的裝置，分別用滑鼠與 Enter 啟用連結。核對草稿收件人後關閉草稿。
3. 在尚未設定郵件 app 的裝置重做，記錄系統及網站的反應。

預期結果：地址與箭頭只有一個鍵盤入口，可選取完整地址；啟用後交由系統處理既有 mailto，已設定的郵件 app 帶入正確收件人，網站不顯示寄送成功訊息，也不直接寄信。

## SITE-R6.7 圖片與相鄰文字

原因：Accessibility tree 可驗證瀏覽器提供的資訊，實際朗讀與閱讀順序仍需以螢幕閱讀器確認。

步驟：

1. 使用 Safari 開啟 production 首頁並啟用 macOS VoiceOver。
2. 依序閱讀 Hero 的職務與公司、About 的三組問答及作品。
3. 開啟標題列表，核對每個問句出現一次。用逐項閱讀核對照片依序提供四張符合畫面的說明。
4. 瀏覽首頁的圖示連結、About 快跳與下載連結，再用鍵盤開關 QR code dialog。
5. 以另一種語言重做以上檢查，並在窄畫面複核問答及照片順序。

預期結果：Hero 的公司名稱由相鄰文字提供，三組問答與四張照片按文件順序朗讀。電腦上的視覺問句不會重複朗讀，照片說明與興趣文字各自提供資訊。控制名稱與描述完整，裝飾 SVG 不增加閱讀項目或鍵盤焦點，關閉 dialog 後焦點回到入口。

## SITE-R6.10 完整訪談閱讀

原因：需要核對雙語事實與問答的閱讀順序。

步驟：

1. 在桌面及窄版的雙語首頁，只靠捲動依序讀完 About。
2. 對照[訪談規格](../../docs/specs/site.md#site-r6-aboutfooter-與部落格)、兩份[首頁字典](../../src/i18n/dictionaries/)及作者提供的資料，核對轉向寫程式的動機、任職公司與產品經驗，以及工作之外的興趣。

預期結果：兩種語言皆能依序讀完三段問答，內容符合作者提供的事實，瀏覽過程只需頁面捲動。

## SITE-R6.11 閱讀進度與快跳

原因：需要人工確認自然捲動時的交接、可見提示與鍵盤操作。

步驟：

1. 用 1440 × 900 視窗開啟 `/#about`。記錄焦點、網址與歷史筆數。
2. 依序向下、快速跨段，再反向捲動。核對問句、段落提示、Header 目前區塊及焦點。
3. 分別用滑鼠、Enter 與 Space 啟用快跳，核對目標落點、焦點、網址與歷史筆數。按 Tab 確認可從目標段落接續操作。
4. 在另一種語言重做。

預期結果：固定問句與段落提示一致，一般捲動時焦點留在原位。啟用快跳後，目標段落捲到 Header 下方並取得焦點，Header 維持 About，網址及歷史筆數維持原值。

## SITE-R6.12 履歷與替代閱讀

原因：需要確認瀏覽器處理下載的方式，以及停用 JavaScript 後的完整閱讀路徑。

步驟：

1. 在兩種語言分別操作 Hero 與 About 第二段的履歷連結，比對下載目的地、檔名與英文內容。
2. 停用 JavaScript 後重新載入首頁，捲過全部問答及四張照片，再操作 About 的履歷連結。

預期結果：兩種語言的兩個入口都取得同一份英文 PDF。繁中靜態首頁仍可依序閱讀三組完整問答與四張照片，也可透過 About 的原生下載連結取得履歷。

## SITE-R6.13 真實作品與說明

原因：需要比較作者作品原始構圖、頁面排列、替代文字與載入失敗時的可讀性。

步驟：

1. 在桌面及手機閱讀 About 第三段。依[照片規格](../../docs/specs/site.md#site-r6-aboutfooter-與部落格)比對順序，依[來源對照](../../src/assets/about/web/provenance.json)找到[原圖](../../src/assets/about/photography/)，比對構圖與比例。
2. 以滑鼠、觸控與鍵盤檢查照片是否有可操作控制。切換兩種語言，核對照片的替代文字。
3. 在開發者工具封鎖同一張照片的各尺寸來源，停用 cache 並重載，檢查預留空間及目前語言的替代文字。

預期結果：第三段在興趣文字後依序顯示四張真實作品，所有照片維持原始比例及構圖，在窄畫面依序排列。照片無操作控制，載入失敗時仍保留原空間及可理解的文字。

## SITE-R7.8 鍵盤操作作品

原因：需要判斷焦點提示及閱讀位置，並確認實際鍵盤操作。

步驟：

1. 用 Tab 聚焦目前作品分頁，按左右方向鍵確認循環切換與焦點。按 Home 與 End 檢查首尾分頁，再以 Enter、Space 選取。
2. 保留分頁焦點並往下捲，按方向鍵、Home 或 End 切換並比對捲動位置。
3. 按 Tab 經過目前展示區、主要目的地與程式碼外連。切換語言後重做。

預期結果：三個作品可用鍵盤操作，焦點與選取一致且有可見提示；切換保持閱讀位置，未選取內容不進入鍵盤順序。

## SITE-R7.9 作品展示層次

原因：產品構圖、素材清晰度、字級與留白需要視覺判斷。

步驟：

1. 在桌面檢視三個作品及兩種語言。
2. 核對名稱、用途、說明、圖片、外連及期間的主次。
3. 確認介面沒有宣傳背景殘留、意外裁切或破圖。
4. 在手機寬度確認圖片出現在說明及操作之前。
5. 在 512 px 以下確認 App 只顯示一個主要畫面。
6. 核對文字及外連沒有被語言切換器遮擋。
7. 檢查真實 Header 與前後區塊的視覺銜接。
8. 關閉 DevTools 的 cache。
9. 啟用 DevTools 的慢速網路。
10. 快速切換三個作品。
11. 確認顯示的是目前作品的預覽，完整圖片載入後清楚顯示，而且頁面高度與焦點保持。
12. 在 512 px 與 513 px 之間調整 viewport。
13. 確認第二張 App 畫面按 breakpoint 顯示，載入過程沒有裁切或明顯位移。

預期結果：三個作品使用一致而節制的展示方式，仍能辨識各自用途；分類及期間維持次要，圖片完整，選取不只靠顏色區分。慢速載入時先顯示目前作品的預覽，切換與調整寬度保持版面及焦點；圖片來源的自動檢查見 SITE-R7.10。

## SITE-R8.1 作品展示

原因：確認實際網站或商店對應目前選取的作品。

步驟：

1. 選取要檢查的作品分頁。
2. 按該作品的主要網站或商店連結。
3. 對照資料核對新分頁 demo URL。

## SITE-R15.2 既有 Registration 清理

原因：自動測試使用隔離的歷史 worker fixture，需要另以真正曾安裝舊版網站的瀏覽器確認 cache、controller 與更新取得方式。

步驟：

1. 使用保留歷史安裝資料的瀏覽器 profile，不要先清除網站資料或 unregister。
2. 記錄瀏覽器、版本、origin、目前網址與 commit。
3. 在開發工具記錄各 registration 的 scope、active、waiting、installing script URL、controller 及 Cache Storage。
4. 檢查舊版網站是否仍由 cache 提供。
5. 以正常線上 navigation 開啟已發布的新版首頁。
6. 確認載入的是新版資源；若舊 worker 仍只提供舊 shell，記錄更新取得失敗，不以手動清除後的結果代替升級通過。
7. 確認同 origin 根 scope 且所有現存 worker 都使用 `/service-worker.js` 的歷史 registration 已移除；只有 waiting 或 installing worker 的紀錄也適用。
8. 確認其他專案 scope、不同 script URL、混合新舊 script 的 registration 均保留。
9. 確認原有 Cache Storage 的內容保留。
10. 確認首頁正常顯示且沒有未處理的 Promise rejection。
11. 若當前頁面仍有舊 controller，記錄舊 controller 的 script URL。
12. 重新開啟首頁；若仍有舊 controller，關閉受控制的頁面後重開。
13. 確認新開啟的頁面已解除舊 controller 的控制。
14. 若歷史安裝位於先前使用的其他 domain，記錄該 origin 的結果，不能從目前 domain 的清理結果推定其他 origin 已移除。

預期結果：新版啟動後只移除符合已知 scope 與所有 script URL 的歷史 registration，保留其他 registration 及 Cache Storage；首頁持續可用，unregister 成功不代表當前頁面立即解除控制，controller 的實際解除時機有紀錄。無法從舊 cache 取得新版時，升級驗證仍待處理。

11. 將視窗改為 390 × 844。

預期結果：在淺色與深色的閱讀背景上，可辨識的焦點框線與相鄰背景的對比至少為 3：1。About 深淺交界的雙層框、快跳與下載連結不受裝飾遮蓋或裁切，強制色彩下使用系統 Highlight。填色按鈕沿用所屬區域的焦點色與外距，滿版目的地的框線留在 viewport 內。

## SITE-R18.3 系統強制色彩

原因：Chromium 的 forced-colors 模擬不能取代 Windows 系統高對比模式的實際顯示。

步驟：

1. 在 Windows 啟用系統對比佈景主題。
2. 開啟 production build。
3. 用鍵盤操作 Header 與窄版選單。
4. 用鍵盤操作 About 快跳、段落目的地、下載連結、作品分頁、展示區、文章及 Footer。
5. 用鍵盤開啟 QR code dialog。
6. 按 Escape 關閉 dialog。

預期結果：各區域均使用系統焦點色，實線框持續可見；品牌色不覆蓋訪客的系統設定，內外距仍讓焦點位置可辨識。

## SITE-R19.2 Escape 關閉提示

原因：需要在實際瀏覽器與鍵盤操作下確認提示關閉後的焦點及重新開啟行為，不能從 Chromium 自動測試推定 Safari、Firefox 或輔助工具的結果。

步驟：

1. 以桌面及窄版畫面，依序 hover Header Logo、語言切換、Hero 社群與 QR code 入口。
2. 按 Escape 後在入口內移動游標，再移出並返回，逐次檢查提示。
3. 用 Tab 或 Shift+Tab 聚焦各入口。游標移入再移出時檢查提示，按 Escape 後核對焦點，移開焦點再聚焦。
4. 窄版選單內有提示時，連按兩次 Escape，分別核對提示、選單及焦點。
5. 在兩種語言及一般、減少動態設定下重做。

預期結果：提示立即顯示，鍵盤焦點仍在入口時，游標移出不會收起提示。Escape 關閉提示且不移動焦點，游標在入口內移動不會立即重開；離開再進入或移開焦點再聚焦後可重新顯示。窄版選單中的提示先由 Escape 關閉，再按 Escape 才關閉選單並將焦點還原至選單按鈕，控制的原有操作保持不變。

## SITE-R19.3 游標移入提示

原因：需要人工判斷跨過提示間距的操作、視窗邊界及 dialog 畫面，並使用 screen reader 確認沒有重複朗讀。

步驟：

1. 在桌面及 320 px 窄版依序 hover Header Logo、語言切換、Hero 社群與 QR code。從入口跨過間距移入提示，再離開。
2. 在視窗邊界的入口觸發提示，檢查提示位置與可見範圍。
3. 開關 QR code dialog，檢查背景提示、入口焦點、重開提示與 Escape 行為。
4. 啟用螢幕閱讀器聚焦各入口，核對名稱與描述。於兩種語言及一般、減少動態設定重做。

預期結果：游標移入提示後，提示仍可閱讀且焦點不變；游標離開入口與提示後，提示收起。提示不超出視窗，底部空間不足時改放上方。Dialog 開啟時入口提示收起，背景提示不蓋住 dialog，關閉後焦點回到 QR code 入口，Escape 可關閉入口提示。Screen reader 保留各控制原有的名稱與描述，不重複朗讀提示文字。

## SITE-R20.1 正文與按鈕對比

原因：對比計算需搭配實際畫面，確認加深文字後仍保有清楚的視覺層級，hover 與鍵盤狀態也保持可讀。

步驟：

1. 在 production preview 分別以 1440 px 與 390 px 寬度開啟首頁。
2. 切換英文與繁體中文。
3. 在各區塊完整顯示的閱讀位置，檢查 About 問句、回答、快跳文字、目前段落提示及履歷連結，再檢查 Hero 的下滑提示及履歷下載。
4. 將游標依序移入 About 快跳與履歷連結、Hero 導覽、社群、QR code、履歷下載及作品控制。
5. 以 Tab 與 Shift+Tab 聚焦上述控制。
6. 開啟 QR code dialog，檢查 dialog 內文字、圖示與焦點，再關閉 dialog。
7. 啟用減少動態後重做一般、hover 與鍵盤狀態檢查。對比量測使用文字或圖示下方實際可見的背景色。

預期結果：About 的白色問句與快跳文字位於深色表面，正文與履歷連結皆清晰可讀。普通文字與背景至少為 4.5：1，大字及必要操作圖示至少為 3：1，焦點符合 SITE-R18。

## SITE-R20.2 履歷次要資訊

原因：瀏覽器的 computed color 檢查無法代替 PDF 的實際閱讀品質，須另確認日期與教育資訊，以及既有版面。

步驟：

1. 在 production preview 從首頁下載履歷 PDF。
2. 在瀏覽器開啟 PDF。
3. 以 100% 檢視整頁。
4. 檢查工作日期、職稱分隔、學歷期間與 GPA 的深灰文字。
5. 依 SITE-R10.2 進入非公開履歷預覽。
6. 使用預覽的列印功能輸出 A4 PDF。
7. 比較兩份 PDF 的文字、字型、連結及單頁版面。

預期結果：預覽與兩份 PDF 的次要資訊均清楚，對比至少為 4.5：1，沒有缺字、裁切或換頁，且維持英文、指定字型、可選取文字及連結。

## SITE-R21.1 圖片右鍵
